# Technology justification

The guiding principle for this proof of concept: **every control a reviewer cares about should be visible in a few lines of code we wrote**, not hidden in framework defaults. Dependencies are kept to the minimum needed, and each one is listed at the end with its reason.

## Backend runtime — Node.js + Express 5

Express has a small surface: a request passes through an explicit, ordered middleware list (`server.js` and `routes/index.js`), so an auditor can read the security pipeline top to bottom: headers → CORS → rate limit → CSRF → auth → role → handler. Express 5 forwards rejected async handlers to the error middleware, so there are no try/catch wrappers to forget. One error handler maps every failure to `{ error: { code, message } }` and logs detail server-side only.

*Rejected alternative: NestJS.* Its decorators and dependency injection give structure, but they hide the order in which guards run and add a lot of framework to explain for a seven-screen PoC.

## Database — MongoDB (Atlas) via Mongoose

The onboarding profile is a document made of nested, repeating sections (roles, qualifications, referees) that will change as the vetting product evolves. That maps naturally to one document per executive, with no join tables. Mongoose gives one place to declare enums, defaults, `select: false` on secrets, and the hooks that make the audit log append-only. Atlas provides encryption at rest, TLS, backups and IP allow-listing on the free tier.

*Rejected alternative: PostgreSQL.* Postgres would give stronger relational integrity and row-level security, and it is a reasonable production choice. Here, though, the nested profile would need 5–6 child tables or JSONB columns, which removes most of the relational benefit, and the brief specified MongoDB.

## Frontend — Next.js (App Router) + React

Next.js deploys to Vercel with no configuration, serves static files with custom security headers (CSP, nosniff, referrer policy) from `next.config.js`, and builds every screen as static output, so the whole UI can be cached as an offline app shell. The service worker is about 90 lines, hand-written in `public/sw.js`, rather than generated by a plugin, so the caching policy is explicit and reviewable. API responses are never cached.

*Rejected alternative: `next-pwa` / Workbox.* They are convenient, but they generate a large opaque service worker and runtime-caching rules that could quietly cache API responses containing PII.

## Auth — JWT in an httpOnly, Secure cookie

- The token is never readable by JavaScript, so an XSS bug cannot steal the session.
- The token is short-lived (30 min) and signed with HS256 with a fixed issuer and algorithm allow-list, which blocks `alg=none` and algorithm-confusion attacks.
- Each request reloads the user from the database, so deactivation and role changes take effect immediately, even with a stateless token.
- Because production is cross-site (Vercel → Render), the cookie is `SameSite=None; Secure`, which re-opens CSRF. The CSRF guard closes it: the Origin must be on the allow-list, and a custom `X-Requested-With` header is required, which a browser can only send cross-origin after a CORS preflight that our policy refuses.
- Locally it falls back to `SameSite=Lax` over http.

*Rejected alternative: JWT in localStorage with a Bearer header.* It is immune to CSRF but fully exposed to XSS, the worse trade for a system holding identity documents.

## File storage — Cloudinary behind `storageService`

Render's free-tier disk is ephemeral, so documents must live off-box. Cloudinary's free tier supports **authenticated delivery**, which means unsigned URLs return 401, plus server-signed, time-limited download URLs. Files are validated before anything leaves the server:
- extension, declared MIME type and magic bytes must all agree;
- max 5 MB;
- files are held in memory only (`multer.memoryStorage`), never written to local disk.

The `storageService` exposes `upload`, `signedUrl` and `remove` and nothing else, so moving to S3 (with pre-signed URLs and SSE-KMS) touches one file.

*Rejected alternative: storing files in MongoDB GridFS.* It would keep everything in one system, but documents would then share the database's blast radius and backup cadence, and every download would stream through the API.

## Styling — Tailwind CSS v4

Utility classes, no component library, and no runtime CSS-in-JS (so the CSP needs no extra style allowances). A dozen shared primitives live in `components/ui.js`.

## Every dependency, and why

| Package | Why it is needed |
|---|---|
| `express`, `mongoose` | framework and ODM (above) |
| `bcrypt` | password hashing, cost 12 (native, constant-time compare) |
| `jsonwebtoken` | sign/verify session tokens with algorithm pinning |
| `cookie-parser` | read the session cookie |
| `helmet` | standard secure headers |
| `cors` | explicit origin allow-list with credentials |
| `express-rate-limit` | brute-force / credential-stuffing throttle |
| `multer` (v2) | multipart parsing into memory with size/count limits |
| `cloudinary` | storage SDK (only imported by `storageService`) |
| `web-push` | VAPID signing and payload encryption for Web Push |
| `zod` | strict server-side schema validation of every write |
| `dotenv` | load `.env` locally (production uses real env vars) |
| dev: `mongodb-memory-server`, `supertest`, `eslint` | hermetic API tests and linting in CI |
| frontend: `next`, `react`, `react-dom`, `tailwindcss` | framework and styling; no other runtime deps (IndexedDB, push and the service worker use browser APIs directly) |
